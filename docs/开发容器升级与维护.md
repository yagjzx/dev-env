# 开发容器升级与维护

> 创建: 2026-03-18
> 适用对象: `dev-env` 仓库维护者、开发机管理员
> 关联文件: `.devcontainer/Dockerfile`, `.devcontainer/docker-compose.yml`, `.devcontainer/entrypoint.sh`, `.devcontainer/requirements-base.in`, `.devcontainer/requirements-base.txt`, `sync/refresh-devcontainer-stack.sh`, `sync/setup-thin-host.sh`

## 一、目标

这套开发容器现在采用“平时锁定、升级时显式刷新”的策略：

- 日常重建时应得到可复现的工具链和基础依赖
- 升级应通过仓库内脚本显式执行，而不是在下次 build 时静默漂移
- 容器应复用宿主机的认证状态，而不是把登录态烘焙进镜像
- 容器 PID 1 必须是可回收子进程的 init，而不是裸 `sleep infinity`

## 二、当前结构

### 2.1 工具链版本

`.devcontainer/Dockerfile` 通过 `ARG` 锁定这些核心版本：

- Python
- Node.js
- Rust
- Go
- Google Cloud CLI
- GitHub CLI
- uv
- gitleaks
- Claude Code
- Codex CLI
- Gemini CLI

这些版本不应手改到“模糊区间”或“latest without review”的状态。升级入口统一走刷新脚本。

### 2.2 Python 基础依赖

Python 基础层分成两层：

- `.devcontainer/requirements-base.in`
  这是人工维护的输入文件，只写顶层依赖。
- `.devcontainer/requirements-base.txt`
  这是用 `uv pip compile` 生成的锁文件，必须提交到仓库。

不要再把 `.txt` 当作人工维护文件直接改。正确做法是改 `.in`，然后重新生成 `.txt`。

### 2.3 认证和挂载

`.devcontainer/docker-compose.yml` 会把宿主机的这些目录挂进容器：

- `~/.claude`
- `~/.codex`
- `~/.gemini`
- `~/.config/gh`
- `~/.config/gcloud`

这意味着：

- 镜像只负责安装 CLI，不负责内置登录态
- 重建容器后，一般不需要重新登录 Claude/Codex/Gemini/GitHub/GCP

### 2.4 进程模型

容器入口链路应保持为：

```text
docker-init -> tini -> /usr/local/bin/entrypoint.sh
```

不要回退到直接以 `sleep infinity` 作为 PID 1。之前出现过大量 zombie，根因就是 PID 1 不负责回收孤儿子进程。

`.devcontainer/entrypoint.sh` 还负责修正 named volume 的权限，尤其包括：

- `/workspace/.venv`
- `/commandhistory`
- `/home/vscode/.cache/uv`
- 多个前端项目的 `node_modules` volume

## 三、标准操作

### 3.1 新机器或全量初始化

使用：

```bash
bash sync/setup-thin-host.sh
```

它会完成：

- 宿主机基础工具安装
- 仓库拉取
- 开发容器 build
- `docker compose up -d --force-recreate`
- 容器内 `post-create` 初始化

### 3.2 修改 devcontainer 配置后重建

优先使用：

```bash
bash sync/setup-thin-host.sh
```

如果只是仓库内维护，也可以直接执行：

```bash
docker compose --env-file .devcontainer/.env -f .devcontainer/docker-compose.yml build dev
docker compose --env-file .devcontainer/.env -f .devcontainer/docker-compose.yml up -d --force-recreate
docker exec -u vscode bladeai-dev bash /workspace/dev-env/.devcontainer/post-create.sh
```

### 3.3 仅刷新版本，不立刻重建

使用：

```bash
bash sync/refresh-devcontainer-stack.sh
```

它会同时做两件事：

1. 刷新 `.devcontainer/Dockerfile` 里的锁定版本
2. 根据 `.devcontainer/requirements-base.in` 重新生成 `.devcontainer/requirements-base.txt`

## 四、升级策略

### 4.1 默认策略

默认命令：

```bash
bash sync/refresh-devcontainer-stack.sh
```

行为：

- Node 走 `current`
- Claude 走 `latest`

适合希望保持新版本工具链的主力开发机。

### 4.2 更稳的策略

如果希望偏稳定而不是偏最新，使用：

```bash
bash sync/refresh-devcontainer-stack.sh --node-channel lts --claude-channel stable
```

适合对 Node current 漂移较敏感，或希望减少 Claude CLI 变动的机器。

### 4.3 升级后的标准动作

每次刷新版本后，都应按下面顺序执行：

1. 查看 `git diff`
2. 重建容器
3. 重新跑 `post-create`
4. 验证 CLI 版本和进程链

建议最少验证：

```bash
docker exec -u vscode bladeai-dev sh -lc 'codex --version && gemini --version && claude --version && python --version && node --version && go version && uv --version'
docker exec bladeai-dev sh -lc "pstree -ap 1 | sed -n '1,12p'"
```

## 五、维护原则

### 5.1 哪些东西应该锁定

应锁定：

- 开发机工具链版本
- Python 基础层依赖解析结果
- 容器入口和权限修复逻辑

不应烘焙进镜像：

- CLI 登录态
- 开发者私有 SSH 密钥
- GitHub / GCP 令牌本体

### 5.2 哪些升级应该显式进行

以下变化都应通过 PR 或明确提交进行：

- Python/Node/Go/Rust 主版本或次版本升级
- Claude/Codex/Gemini CLI 升级
- `requirements-base.in` 顶层依赖变更
- `requirements-base.txt` 重新编译

不要让这些变化只发生在某台开发机本地、却不回写仓库。

## 六、已知行为与排查

### 6.1 `GH_TOKEN` warning

`docker compose` 可能提示：

```text
The "GH_TOKEN" variable is not set. Defaulting to a blank string.
```

这不一定是故障。如果 `~/.config/gh` 已挂进容器，且 `gh auth status` 正常，容器内仍可使用 GitHub CLI。

### 6.2 `post-create` 里的 uv 权限错误

如果出现类似：

```text
Failed to initialize cache at /home/vscode/.cache/uv
```

先检查：

- 是否使用了最新的 `.devcontainer/entrypoint.sh`
- 是否执行了 `docker compose ... up -d --force-recreate`

该问题通常是 named volume 权限未被重新修正导致。

### 6.3 容器“正常启动”但没有业务服务

这是设计使然。`bladeai-dev` 是开发工作台容器，不负责自动拉起各仓库的业务服务。它默认只提供：

- 工具链
- 工作区
- 认证挂载
- `post-create` 初始化

如果需要某个项目常驻运行，应在对应项目或进程管理器里单独定义，而不是假设 devcontainer 会自动启动全部应用。

### 6.4 再次出现 zombie

优先检查：

```bash
docker exec bladeai-dev sh -lc "pstree -ap 1 | sed -n '1,12p'"
docker exec bladeai-dev sh -lc "ps -eo stat= | awk '\$1 ~ /^Z/ {count++} END {print count+0}'"
```

如果 PID 1 链不是 `docker-init -> tini -> entrypoint`，或者 zombie 数持续增长，说明入口或 compose 配置被改坏了。

## 七、推荐维护流程

建议按这个节奏维护：

1. 平时保持仓库内版本锁定
2. 需要升级时，运行 `bash sync/refresh-devcontainer-stack.sh`
3. 审查差异后重建容器
4. 验证通过再提交

这样可以同时满足：

- 开发机一致性
- 故障可复现
- 升级可审查
- 新机器可一键落地
